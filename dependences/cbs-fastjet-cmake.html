FastJet & fjcontrib

What changed in how the build obtains, links and selects the jet-clustering stack — and why that is a three-way comparison rather than a two-way one. Upstream master ships fjcore only; the private-SUSYRun2 source branch replaced it with a downloaded FastJet; this branch keeps both and decides at configure time.

01 · three states

fjcore, then FastJet, then both

Comparing only against the source branch would make the fjcore fallback look like an invention. It is a restoration — of exactly what upstream master still does.

The source branch's own comment said why it had to choose: "Temporarily comment while fastjet is a contrib, as there are class name clashes." The two libraries could not coexist under one namespace, so one had to go. Routing every use through the FJNS macro is what makes keeping both possible.

02 · the obvious question

Why fjcore is still here

Keeping a second jet-clustering library costs compile time and one more thing to reason about. Three reasons it stays, and one common explanation that the tree does not support.

ReasonEvidenceWhat it buys
It is upstream's only jet backend gambit/master has no FastJet in cmake/contrib.cmake at all — fjcore, unconditional, -DFJCORE -DFJNS=gambit::fjcore. A configuration that matches upstream still works here. Dropping fjcore would have made this branch unable to build the way master builds.
It is the no-FastJet floor The else() branch of the probe, which is now reachable in normal use because CMake no longer downloads FastJet. GAMBIT still configures and compiles on a machine that has not provisioned FastJet. This matters more after change 2, not less.
Coexisting is nearly free fjcore.hh:173 — #define FJCORE_BEGIN_NAMESPACE namespace gambit { namespace fjcore { fjcore lives in gambit::fjcore, FastJet in fastjet. The namespaces are disjoint by construction, so both can be compiled into one binary.

That last row is what makes the whole arrangement possible, and it also explains the source branch's comment — "Temporarily comment while fastjet is a contrib, as there are class name clashes". The clash was never between the definitions; it was between unqualified uses of PseudoJet and ClusterSequence, which exist in both namespaces. Routing every use through FJNS makes each one qualified, and the clash disappears.

fjcore is compiled and linked whether or not FastJet was found: contrib.cmake:328 puts it in GAMBIT_BASIC_COMMON_OBJECTS, which every GAMBIT executable links. So the cost is paid on every build; only the namespace choice is conditional.

The explanation that does not hold up: "other modules still need fjcore". Counting every file that names a jet type at all — PseudoJet, ClusterSequence or FJNS — gives this:

Under -DFJCORE, FJNS becomes gambit::fjcore while the three fastjet:: qualifiers stay literal — and that namespace no longer exists in the translation unit. It is the template worth copying: one idiom to fix in 5 files, not a rewrite.

The two consumption sites disagree on link order. executables.cmake appends fjcontrib before FastJet; utilities.cmake appends FastJet before fjcontrib. With static archives — and libRecursiveTools.a, libEnergyCorrelator.a and libVariableR.a are static on this machine — a left-to-right resolver such as GNU ld wants the dependent archive first. It is not observed to fail here; macOS ld64 does not require that order, and libfastjetcontribfragile is a shared object that may resolve the symbols anyway. Flagged because the two sites disagree, which is a difference no one chose.

06 · the gap

Nothing in this repository provides FastJet any more

The download step was removed. The ignore rules that made sense while CMake downloaded the tarballs are still in place.

On a fresh clone the probe fails and the build keeps going. The else() branch sets the three exclusion variables and prints nothing — the old code printed a message on its exclusion path, this one does not. The first visible symptom is Rivet announcing its exclusion, which names FastJet but reads like a Rivet problem. A collaborator who wants what this branch does has to provision contrib/fastjet-3.4.2/local themselves; that step now lives in neither the build system nor the repository.

The fallback is a build fallback, not an analysis fallback. Of the analyses that use these algorithms, 3 carry an #ifndef FJCORE include guard and 7 carry none. Even the guarded ones only switch their includes: Analysis_ATLAS_EXOT_2016_014.cpp still writes FJNS::contrib::EnergyCorrelator in the body, and fjcore has no contrib namespace to provide it. Read from source, not from a compiler — no build was attempted — but the guard does not appear sufficient.

Adjacent work by another author points at the same problem from the other side: cmake/scripts/copy_tarballs.sh and restore_tarballs.sh (ChrisJChang, 2025-12) collect downloaded tarballs into one folder and put them back, and safe_dl.sh gained a project-source-directory argument to support it. That is a caching mechanism for things CMake still downloads — it does not cover FastJet, which CMake no longer downloads at all.
