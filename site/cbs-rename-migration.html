The naming migration

Every analysis moved from a name describing what it looked at to the report number of the paper it reproduces. The deck quotes the file count. This page carries the other number — the one a YAML actually depends on — the full old-to-new table, the files that absorbed several analyses each, and the two analyses whose source says plainly why they did not move.

Two counts describe this migration and they are not the same. Files are what git diff -M reports. Registered names are what DEFINE_ANALYSIS_FACTORY emits and what a YAML selects by — a single file can register several. The second number is larger, and it is the one that describes what breaks.

01 · two levels

The file count understates it

Both numbers are correct; they measure different things.

LevelBaselineHeadWhat it means
Files git calls renames—75 Detected by content similarity. Misses a move when the file was also rewritten, or when several files folded into one.
Files with a provenance block—80 The migration wrote // Renamed from: into each file. This is the migration's own record, and it is more complete than git's.
Registered analysis names128137 What DEFINE_ANALYSIS_FACTORY emits — the string a YAML writes. 123 retired, 132 introduced, 5 survived.

The gap is the consolidations. 18 files each absorb more than one old analysis file — 56 old files in total — and a fold-in is not a rename, so git reports the survivor as modified and the others as deleted. That is why the deck's 75 and this page's 80 disagree, and neither is wrong.

02 · the scheme

From what it looked at, to how it is cited

Both schemes pack four fields into the name. They pack different ones.

Report typeFilesShareWhat it is
SUSY4151%ATLAS supersymmetry paper
SUS2734%CMS supersymmetry paper
CONF68%ATLAS conference note — preliminary, not a journal paper
B2G22%CMS beyond-two-generations paper
EXO22%CMS exotics paper
unparsed11%does not fit the scheme (see below)
EXOT11%ATLAS exotics paper

The new name is unambiguous in a way the old one was not: ATLAS_13TeV_0LEP_36invfb describes a search, but several papers match that description, whereas ATLAS_SUSY_2016_07 resolves to exactly one. The cost is that it no longer says what the analysis selects — you have to look it up. The CONF and PAS entries are worth noticing: those are preliminary notes rather than journal papers, and a report number does not change that.

This is the part most easily misread. When four old files fold into Analysis_CMS_SUS_19_012.cpp, no analysis is lost: the file defines a base class and one subclass per signal-region grouping, each with its own DEFINE_ANALYSIS_FACTORY. What changed is that the sub-region names now derive from the report number too — CMS_SUS_19_012_3Lep rather than CMS_13TeV_MultiLEP_3LEP_137invfb. So a YAML naming a sub-region breaks in exactly the same way as one naming a parent.

That is the right way to leave an exception: the next person does not have to guess whether it was missed or deliberate. The remaining survivors are test and utility stubs with no paper behind them.

06 · what this breaks

Old names do not resolve any more

A YAML selecting an analysis by name gets a name that no longer exists. There is no alias table in the tree.

Tracked YAMLDead namesExamples
yaml_files/PX_SUSYRun2_stop.yaml48ATLAS_13TeV_0LEPStop_139invfb, ATLAS_13TeV_0LEP_139invfb, ATLAS_13TeV_1Lep2b_139invfb, ATLAS_13TeV_1OR3LEP_StopHZ_139invfb … and 44 more

Only 1 tracked YAML is affected, but it is affected badly: yaml_files/PX_SUSYRun2_stop.yaml names 48 analyses that no longer exist. It would fail at configure time today. That file is the in-tree evidence of the cost — every configuration outside this repository that selects analyses by name has the same problem and no warning.

This is the decision for the collaboration, not for this branch. Report-number naming is unambiguous and matches how the papers are cited, but 123 retired names means every existing configuration that selects analyses by name has to be rewritten. Whether upstream wants the migration, and whether it should ship with an alias table mapping old names to new for one release, is a group call. The migration itself is complete and self-documenting — every moved file records where it came from — which is what makes an alias table cheap to generate later if the group wants one.

07 · boundary

What this page does not tell you

Read from the tree, not from a running build.

Names, provenance comments and factory registrations are read from the worktree as text. Nothing was compiled, no analysis was instantiated, and no event was processed — so this page shows that a name changed, not that the analysis behind it still produces the same yields. The similarity percentages come from git diff -M and describe textual overlap only; a 60% move is not evidence that 40% of the physics changed, and the low-similarity entries are worth opening individually before anyone says otherwise.
