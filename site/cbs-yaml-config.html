The shape of the change is not “shorter”. This branch added a required setting the original never had — jet_collections, read with getValue so a missing one throws — and jet configuration is verbose: three collections is 22 lines. Left alone, every user file would have grown. The default card exists to absorb the requirement this branch created, and separately the convergence block that used to be the user’s business stopped being the user’s business. Those are two different movements and the file diff shows neither.

03 · what CBS decides for you

Three settings the YAML cannot reach

solo.cpp builds the collider options node from the user settings and then writes over it.

KeyForced toLineReason in the source
min_nEvents(long long)(1000)383—
max_nEvents(long long)(std::numeric_limits<int>::max())384—
run_convergence_checksfalse386CBS policy: always process all events provided by the user (no convergence-based early stop).

This is the one to say aloud. run_convergence_checks is forced to false, so CBS always processes every event the user supplied and never stops early. That makes the whole convergence group from the original file inert — target_fractional_uncert, halt_when_systematic_dominated, all_analyses_must_converge, all_SR_must_converge, events_between_convergence_checks are still read, still have defaults, and no longer change what a CBS run does. The event loop was edited to match: ColliderBit_eventloop.cpp:197 keeps target_fractional_uncert mandatory when convergence checks are on, and falls back to 0.30 when they are off, with the comment “For explicit no-convergence runs (CBS policy), this value is unused.”

A user carrying an old file forward will not be told any of this. The keys still parse, so nothing warns; they simply stop meaning anything. Worth a line in the CBS documentation rather than leaving it to be discovered.

05 · one switch, two consequences

check_histogram does not mean the same thing twice

Read once at solo.cpp:179 with getValueOrDef<bool>(false, …) and set on a static that every analysis shares. The default is false.

Histogram kind check_histogram: false — the default check_histogram: true What the flag actually costs
plainobs empty Not booked, not filled, not written. Nothing in the JSON, nothing to plot. Appears under histograms.1d with counts and sumw2. output only Signal regions are identical either way. Turning it on adds a diagnostic and changes no result.
signal regionobs / bkg / bkg_err set Same as above — and COMMIT_HISTOGRAM_SRS never runs, so the per-bin regions do not exist. Appears in the JSON and every bin is added as a SignalRegionData. changes the likelihood The analysis contributes a different number of signal regions depending on this flag.

Both rows are live in this branch. ATLAS_EXOT_2019_04, ATLAS_EXOT_2019_07 commit histogram-backed signal regions, so the flag moves their likelihood; ATLAS_EXOT_2021_35 books plain histograms only, so the flag decides whether a plot exists and nothing more. A reader cannot tell which case they are in from the YAML — the key looks the same in both, and the analysis source is the only place the difference is written down.

Only the fill macros are self-guarding. FILL_HISTOGRAM_1D and FILL_HISTOGRAM_2D expand to if (Histogram1D::check_histogram()) …, and Histogram1D::fill checks again at Histogram.hpp:148. Booking and committing are not guarded by the macro — each analysis writes if (Histogram1D::check_histogram()) around them by hand.

The failure mode this leaves open. An analysis that books and commits signal-region histograms without the hand-written guard would, with the flag off, still create the histogram and still commit its bins — but the fills would all have been skipped. The result is a full set of per-bin signal regions with a signal prediction of exactly zero in every bin. That is not a crash and not a missing key; it is a likelihood built on empty predictions, and nothing in the framework would report it. All three current consumers do write the guard, so this is a latent hazard rather than a present bug — but the guard belongs inside COMMIT_HISTOGRAM_SRS, where it cannot be forgotten.

06 · the default card

Three layers, user wins

CBS_yaml/CBS_defaults.yaml, 22 lines of settings in the working tree.

LayerWhat it contributes
1 · globalCBS_defaults.yaml → settings:
2 · per analysisanalysis_defaults: <NAME>:, merged in the order the analyses appear in the user's YAML
3 · userthe input file — always last, always wins

merge_yaml_nodes (solo_input.cpp:62) recurses through maps, but scalars and sequences are replaced whole: a list can be overridden, never appended to. Lookup for the defaults file runs five steps — cbs_defaults_file:, $CBS_DEFAULTS_FILE, then three paths — and use_cbs_defaults: false opts out entirely.

The defaults file is not in the repository. .gitignore ignores CBS_yaml/* and git ls-files CBS_yaml/ is empty, so a fresh clone has no CBS_defaults.yaml. All five lookup steps then fail and apply_default_settings returns the user settings unchanged and silently (solo_input.cpp:130). The run dies later at Utils.hpp:96 with “Could not find jet_collections option. Please provide this in the YAML file” — pointing the user at their own file rather than at the missing defaults. Committing the card, or printing one line when the lookup fails, would close this.

07 · boundary

What this page does not tell you

Each key is placed by the call that reads it, found by scanning four source files for getValue and getValueOrDef. That is a textual match, not an execution trace: a key consumed through some other path would be reported as unread, and the “dead key” verdict means only that no .cpp or .hpp in the repository names it at either ref. Nothing was compiled and no run was performed, so this page describes what the code says it will do with a setting, not what a run then produces.
