Variable-R jets

How a variable-R jet collection was threaded through ColliderBit: what it depends on, which files it touches, what was filled in at each stage, and the three places where it deliberately does nothing. A VR jet has no fixed radius — its catchment is rho / pT, clamped between Rmin and Rmax — and almost every decision below follows from that one fact.

The existing lane was not edited

The fixed-R body is 336 tokens at the baseline and 336 now, agreeing to 99.40%. The whole of the difference sits on one line, L308: const FJNS::JetDefinition jet_def(jet_algorithm, jetcollection.R, jet_strategy, jet_recomscheme); became const FJNS::JetDefinition jet_def(jet_algorithm, jetcollection.R, jet_recomscheme, jet_strategy); — a two-argument reorder that arrived in bb641a5d1e, an unrelated commit that fixed a deprecated FastJet call signature. Comparing tokens rather than lines is deliberate: a clang-format pass swept this file, so a line diff would report hundreds of changes that say nothing.

One entry, one exit

The branch opens at L220 and closes at L301 with a continue. There is no VR test anywhere else in the function, no VR flag threaded through a helper, and no second loop. Delete those 82 lines and the function is the baseline function again.

No new type

VR added 4 fields to the existing jet_collection_settings rather than a new struct, a variant or a subclass. The pre-existing fields gained defaults at the same time — that is what lets one struct serve both lanes, since a VR collection never sets R, recombination_scheme or strategy.

The output is the same object

Both lanes end on a byte-identical result.add_jet(new HEPUtils::Jet(pj, tags), jetcollection.key). There is no VRJet type and no separate container. An analysis calling event->jets(key) gets HEPUtils::Jet either way and cannot tell which lane produced it.

The differing rows are worth reading for why they differ. Four of them are the flavour-tagging radii, and they differ for a physics reason rather than a structural one: the fixed-R lane matches b and c inside a hard-coded 0.4 and τ inside 0.5 — constants that ignore the collection’s own R, and that carry @todo Hard-coded radius!!! in the source — while the VR lane matches inside effectiveR, the radius that actually produced the jet. A single cone cannot serve a 20 GeV and a 500 GeV VR jet; using one would mistag them in opposite directions.

04 · what was filled in

Seven additions, stage by stage

One card per stage, with the reason it was needed and the source it produced.

1 A jet collection became a named, typed thing YAML Utils.hpp
what
jet_collection_settings carries 9 fields. A fixed-R collection reads R, recombination_scheme, strategy; a variable-R one reads rho, Rmin, Rmax, pt_min instead. The algorithm string decides which branch runs, so the two parameter sets never mix.
why
VR jets are not a fixed-R jet with a different number in the R slot. They have no single R at all — the radius is a function of rho and the jet's own pT, clamped between Rmin and Rmax. Reusing the R field would have made a meaningless value mandatory.

4 Flavour tagging by the jet's own radius conversion Py8EventConversions.hpp
what
b, c and τ association uses effectiveR = min(Rmax, max(Rmin, rho / pT)) — the radius that jet actually had — instead of a fixed cone. W, Z and h association still uses a hard-coded ΔR < 1.0, marked @todo Make selectable? in the source.
why
Matching a 20 GeV VR jet and a 500 GeV VR jet with the same cone would mis-tag both, in opposite directions. The whole point of a variable radius is that the catchment shrinks with pT, and the tagging has to follow it.

6 VR collections opt out of detector smearing detector BuckFast.cpp
what
std::vector jetcollections_no_smear; is filled from the VR collection keys, and BuckFast skips those collections in two loops: jet-momentum smearing, and the pass that clears b-tags outside |η| > 2.5.

The BuckFast jet smearing is tuned for calorimeter jets with a fixed radius. VR track jets are a different object with different resolution, so applying the same smearing would be worse than applying none.

06 · the boundaries

Where VR jets deliberately do nothing

Four sites skip VR collections on purpose. Each is a physics decision written as a continue.

SiteSourceReason
Py8EventConversions.hpp:519if (is_vr_algorithm(jetcollection.algorithm)) continue;no tracks exist at this level to cluster
lhef2heputils.cpp:111if (is_vr_algorithm(jetcollection.algorithm)) continue;no tracks exist at this level to cluster
BuckFast.cpp:48if (std::find(jetcollections_no_smear.begin(), jetcollections_no_smear.end(), jetcollection) != calorimeter-jet smearing does not describe VR track jets
BuckFast.cpp:56if (std::find(jetcollections_no_smear.begin(), jetcollections_no_smear.end(), jetcollection) != calorimeter-jet smearing does not describe VR track jets

What “skipped” actually costs. Only the jet passes are per-collection. Electrons, muons and taus are smeared once per event, outside the loop, so the opt-out never touches them — it is jets and nothing else. For a fixed-R collection, smearJets draws a Gaussian factor centred on 1 and scales the momentum, with a fractional width read from a pT-binned table: 0.145 below 50 GeV falling to 0.04 above 1 TeV, with no η dependence at all (ATLASEfficiencies.hpp:124, one η bin, sourced from ATLAS-CONF-2015-017). A VR collection receives none of that, so VR jets leave the detector model at their truth momentum.

That is a deliberate choice between two wrong answers rather than a correct one. The table above is a calorimeter jet energy resolution; a VR track jet is built from tracks, where the resolution is better at low pT and degrades with pT instead of improving. Applying that curve to a track jet would be wrong in the wrong direction, so the code applies nothing — but nothing is still optimistic: analyses currently see VR jets sharper than any real detector would deliver. A track-jet resolution model is the missing piece, and this should be said aloud rather than discovered by a referee.

The second loop has a separate consequence. It is the pass that clears b-tags outside |η| > 2.5, so a VR jet keeps whatever b-tag the truth matching gave it, at any η. Both pipeline analyses cut abseta() < 2.5 themselves before using VR jets, so the effect does not reach them — but an analysis that forgets that cut would inherit b-tags the detector model was supposed to have removed.

07 · the consumers

Three analyses, two ways of asking

All three are new on this branch. Two take the collection the pipeline built; one builds its own.

AnalysisLinesWhere its VR jets come from|η|<2.5 cut sites

The exception is the caveat from the deck, made concrete. ATLAS_SUSY_2018_07 constructs its own VariableRPlugin with rho, Rmin and Rmax hard-coded in the analysis body. It works, but YAML cannot reach it: changing the collection definition in the input file changes nothing for that analysis, and it does not appear in event->jet_collections(). It is also outside every opt-out above — the no-smear list is keyed by collection name, and this collection has no name.

The recommendation that follows is the one already on the slide: declare the collection in YAML and read it with event->jets("<key>"). That is the path the validation, the tagging and the detector opt-outs all understand.

08 · boundary

What this page does not claim

The usual limits, stated rather than implied.

This page describes code paths, not results. No CBS binary was built for it and no events were clustered. It does not show that the VR jets produced here match ATLAS's, that the effective-radius flavour matching reproduces the published tagging efficiencies, or that the b-tag working points used in the analyses are right. Those are validation questions and need a run with real events on both sides, which is a separate exercise.

What it does establish, from source: which files a VR collection passes through, what each stage contributes, which YAML keys are mandatory, what the configuration refuses, and the four places where VR is deliberately absent.
