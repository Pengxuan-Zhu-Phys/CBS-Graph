What counts as "my change"

The branch carries 606 commits that master does not — but only 226 of them were authored here. Every number in this deck is attributed per file, so merged upstream work is never counted as local work.

Why this deck exists alongside the branch-comparison graph. The existing tree-diff comparison has no rename detection, so it reports each of the 75 renamed analyses twice — once as "deleted on the left", once as "added on the right", inflating the apparent churn by ~150 files. This ledger asks Git directly with -M, so a rename is one moved file.
Evidence boundary. Everything here comes from Git history and current source text. Nothing was recompiled or re-run: this is a record of what changed in the code, not a measurement of what changed in the physics output.

05 · new capability

The standalone runner

+2,978 lines across ten files, none of which exist upstream. This is the single largest structural addition on the branch.

Input model

settings.processes — each with name, cross section, uncertainty and a list of HepMC files. Event counts are read from the files; generated_events is explicitly rejected as an event-count source.

Batch semantics

Each physical file becomes a subprocess retaining its full process cross section. Merging validates luminosity, background, SR label order and histogram structure before combining.

Sampling advice

Batch runs report effective event counts and how many more events each process needs to hit a target fractional uncertainty.

06 · new capability

Results became a data contract

Cutflows, histograms and signal regions used to be per-analysis conventions living as C++ objects. They are now shared types with a versioned serialisation.

Histogram.hpp · 678 lines · local

Weighted fill with sumw2, under/overflow bins, scale, combine, attached obs/bkg/bkg_err, and to_signal_regions() so a shape distribution converts directly into binned SRs.

Cutflow.hpp · +48 · local

Consolidated from per-analysis implementations. A runtime settings.check_cutflow switch replaces "depends how you compiled it"; the CMake CUTFLOW option now only reports capability.

AnalysisMacros.hpp · +55 · local

DEFINE_HISTOGRAM_1D, DEFINE_HISTOGRAM_SR_1D, 2D variants and FILL_HISTOGRAM — so a new analysis declares distributions rather than hand-rolling them.

The practical consequence: one pass over the events now yields cutflow, cut-and-count SRs and shape histograms simultaneously, and post-processing never has to re-read HepMC.
Line-level companion page

"A versioned serialisation" is the claim; cbs-solo-loglike-v1 · the JSON output contract ↗ is the contract itself — eight top-level keys, 106 fields, and the flags that tell a consumer which log-likelihoods may be added together. Nothing to compare against: SUSYRun2 has no json.hpp at all.

08 · analysis layer

The naming migration

75 analyses moved from descriptive names to publication report numbers, each carrying a // Renamed from: provenance comment. Total churn +4,699 / −4,918 — overwhelmingly the move itself, not rewritten physics.

Why it matters for this comparison

A plain tree diff cannot see these as moves. The existing branch-comparison page lists each old name as "added in SUSYRun2" and each new name as "added in solo" — 150 phantom file changes. Git's rename detection collapses them to 75 moves at 52–100% similarity.

Five commits did this work: ccf24b2959, 89d33f9c2d, 07e7fb207e, f18f1e5cb8, b76aecc71e (the last aligning .info metadata).

10 · completion boundary

What is not finished

Registered in the framework is not the same as reproducing the published analysis. Three things should be said plainly rather than discovered later.

skeleton

ATLAS EXOT-2018-60

38 lines. run() contains only // TODO: Implement the published selection and signal-region yields. and collect_results() is empty.

Say: the analysis entry and metadata exist; the physics selection does not.

partial

CMS B2G-18-003

3M regions use five-jet-mass histogram SRs digitised from Fig. 4(c,d). 3T and 2M1L histograms are scaffolded with empty obs/bkg vectors pending digitisation. High-mass regions are a public cut-and-count approximation, not the CMS shape fit.

Say: the framework path is proven; the external data is incomplete.

approximation

b-tag proxies

B2G-18-003 approximates soft-drop subjet b-tagging with AK4-associated proxy subjets — documented in the source as a public-recast approximation.

Say: this is a recast choice, and it is written down in the code.

Phrasings to avoid tomorrow. Do not describe registration in AnalysisContainer as a completed analysis. Do not present B2G-18-003's empty obs/bkg arrays as a finished reproduction. Do not quote the +313k line count against master — it is dominated by two background JSON files (152k + 86k lines) and a vendored json.hpp.
What this deck does not measure. Nothing here was recompiled or re-run. It shows that code changed and who changed it — not which physics results moved. A before/after data-flow comparison on identical input events is the natural next step, and would answer the question this ledger can only frame.

Runtime data-flow diff

This ledger answers what code changed. It cannot answer which events now take a different path — the question that actually matters for validation.

A thin semantic tracer at ~10–20 checkpoints (HepMC event → HEPUtils event → object selection → overlap removal → b-tagging → cuts → signal region), emitting JSON per run, would let the same input events be run on two commits and diffed:

overlap removal ← CHANGED
  jets 6 → 4
  Njet ≥ 5: PASS → FAIL
  SR1 acceptance 0.132 → 0.119

That is a far stronger argument to a collaborator than a diff — and it reuses the JSON output contract this branch already built.
