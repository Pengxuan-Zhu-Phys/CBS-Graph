05 · new capability

The standalone runner

+2,978 lines across ten files, none of which exist upstream. This is the single largest structural addition on the branch.

Input model

settings.processes — each with name, cross section, uncertainty and a list of HepMC files. Event counts are read from the files; generated_events is explicitly rejected as an event-count source.

Batch semantics

Each physical file becomes a subprocess retaining its full process cross section. Merging validates luminosity, background, SR label order and histogram structure before combining.

Sampling advice

Batch runs report effective event counts and how many more events each process needs to hit a target fractional uncertainty.

CBS policy

Three keys the YAML cannot reach

These are forced policy keys, not dead code. solo.cpp builds the options node from the user settings, then writes over it:

  • min_nEvents → 1000 · max_nEvents → INT_MAX
  • run_convergence_checks → false — always process all supplied events

That makes the whole convergence block inert — five keys that still parse, still have defaults, and no longer change what a CBS run does.

Dead keys — no reader in any current C++ file: covariance_marg_convthres_abs, covariance_marg_convthres_rel, covariance_nsamples_start.

default cards

Three layers, user wins

For optional scalar controls, getValueOrDef(default, key) falls back to the program default. The lookup runs CBS_defaults.yaml → settings:, then analysis_defaults: <NAME>: in analysis order, then the user file. merge_yaml_nodes (solo_input.cpp:62) recurses through maps but replaces scalars and sequences whole — override a list, never append to one.

This does not make required inputs optional: the event source, cross-section and required jet configuration are still validated separately.

So ATLAS_EXOT_2019_04.yaml names no jet collection at all, including the variable-R one: the card supplies 22 lines the user never sees.

The card itself is not in the repository. .gitignore:50 ignores CBS_yaml/*, so on a fresh clone all five lookup steps fail, apply_default_settings returns the user settings unchanged and silently (solo_input.cpp:130), and the run dies at Utils.hpp:96 blaming the user’s own YAML for the missing jet_collections.

07 · new capability

Results became a data contract

Cutflows, histograms and signal regions used to be per-analysis conventions living as C++ objects. They are now shared types with a versioned serialisation.

Histogram.hpp · 678 lines · local

Weighted fill with sumw2, under/overflow bins, scale, combine, attached obs/bkg/bkg_err, and to_signal_regions() so a shape distribution converts directly into binned SRs.

Cutflow.hpp · +48 · local

Consolidated from per-analysis implementations. A runtime settings.check_cutflow switch replaces "depends how you compiled it"; the CMake CUTFLOW option now only reports capability.

AnalysisMacros.hpp · +55 · local

DEFINE_HISTOGRAM_1D, DEFINE_HISTOGRAM_SR_1D, 2D variants and FILL_HISTOGRAM — so a new analysis declares distributions rather than hand-rolling them.

The practical consequence: one pass over the events now yields cutflow, cut-and-count SRs and shape histograms simultaneously, and post-processing never has to re-read HepMC.

09 · analysis layer

Histograms, and histogram signal regions

One new class does two jobs. Booked one way it is a diagnostic object. Booked the other way every bin becomes a signal region that enters the likelihood — and the difference is whether one vector is empty.

plain histogram

obs empty

Bins, weights, under/overflow. Reaches the run JSON and the plotting script and stops there. is_signal_region() is false; nothing downstream reads it as physics.

Used by ATLAS_EXOT_2021_35 — two uniform mVLQlep histograms alongside its 2 cut-and-count SRs, which the histograms do not change.

signal-region histogram

+ obs / bkg / bkg_err

to_signal_regions() turns each bin into a SignalRegionData named <hist>_bin<i>, carrying that bin's observed count, its own content as signal, the published background, and sqrt(sumw2) as the MC error.

Used by ATLAS_EXOT_2019_04 (mVLB, 7 bins) and ATLAS_EXOT_2019_07 (mJJ, 16 bins).

The two numbers, and why both are right

Files are what git diff -M reports: 75. Registered names are what DEFINE_ANALYSIS_FACTORY emits — the string a YAML writes — and one file can register several. 128 at the baseline, 137 now, 123 retired.

The gap is 18 consolidations: files that absorbed several old analyses each, 56 old files in total. A fold-in is not a rename, so git reports the survivor as modified and the rest as deleted. No analysis was lost — each sub-region still registers separately, it just lives in the report-number file now.

The one that stayed, and the one still broken

ATLAS_8TeV_1LEPbb_20invfb is the only physics analysis that kept its old name, and the file says why: "unrenamed, can not find original exp report". That is the right way to leave an exception — the next person does not have to guess whether it was missed or deliberate.

yaml_files/PX_SUSYRun2_stop.yaml still names 48 analyses that no longer exist. It would fail at configure time today — in-tree evidence of what the migration costs every configuration outside this repository.

13 · completion boundary

What is not finished

Registered in the framework is not the same as reproducing the published analysis. Three things should be said plainly rather than discovered later.

skeleton

ATLAS EXOT-2018-60

38 lines. run() contains only // TODO: Implement the published selection and signal-region yields. and collect_results() is empty.

Say: the analysis entry and metadata exist; the physics selection does not.

partial

CMS B2G-18-003

3M regions use five-jet-mass histogram SRs digitised from Fig. 4(c,d). 3T and 2M1L histograms are scaffolded with empty obs/bkg vectors pending digitisation. High-mass regions are a public cut-and-count approximation, not the CMS shape fit.

Say: the framework path is proven; the external data is incomplete.

approximation

b-tag proxies

B2G-18-003 approximates soft-drop subjet b-tagging with AK4-associated proxy subjets — documented in the source as a public-recast approximation.

Say: this is a recast choice, and it is written down in the code.

Phrasings to avoid tomorrow. Do not describe registration in AnalysisContainer as a completed analysis. Do not present B2G-18-003's empty obs/bkg arrays as a finished reproduction. Do not quote the +313k line count against master — it is dominated by two background JSON files (152k + 86k lines) and a vendored json.hpp.
What this deck does not measure. Nothing here was recompiled or re-run. It shows that code changed and who changed it. For the paths that already existed that is close to the whole story — CBS changes how ColliderBit is called, not the physics it runs — but for the new analyses above, "the code is there" and "the numbers match the paper" are different claims, and only the first is evidenced here.

14 · open design question

Getting CBS onto someone else’s machine

The work is done when a collaborator can run it. Today that is the hardest part of CBS, and it is not a C++ problem — it is a provisioning problem. Raising it here because the fix is a design decision, not a patch.

the barrier

69 backends for a runner that needs a handful

cmake/backends.cmake declares 69 backends. CBS declares MODULES ColliderBit DEPENDENCIES hepmc pybind11. A new user has to navigate the gap themselves, with -Ditch and -DBits as the only map.

contrib.cmake builds HepMC, YODA and RestFrames from source through ./configure — the step that fails differently on every macOS and every Linux. GAMBIT_USE_LLD_FOR_CBS exists because linking CBS was itself worth an option.

hepforge

29 of 71 download URLs, one host

41% of backend downloads point at hepforge.org. When it is slow or down, configure fails partway and leaves a half-populated tree — and the user cannot tell a network problem from a build problem.

Half the mitigation already exists, from master: safe_dl.sh falls back across axel/wget/curl and accepts a secondary URL; copy_tarballs.sh and restore_tarballs.sh build an offline mirror. Nothing tells a user these are there.

and it fails quietly

Two silent failures we already found

Slide 12: the FastJet probe has an empty else(). A fresh clone falls back to fjcore without a word; the first symptom is Rivet announcing its own exclusion.

Slide 6: CBS_defaults.yaml is gitignored, so the defaults lookup fails silently and the run dies later blaming the user’s own YAML.

Both fail late, and neither names the real cause. That is the difference between a hard build and an unexplained one.

Proposal, for discussion — not built. (1) Declare a CBS-minimal dependency set as a named CMake preset, so the answer to “what do I need?” is one file rather than 69 entries and two ditch flags. (2) One command — ./cbs-setup — that probes the machine, prints one table of what it found and what is missing, and provisions the rest. (3) Move every check to configure time and fail loudly with the cause named; no silent fallback that surfaces as an unrelated error an hour later. (4) Take HepForge off the critical path: pin, checksum, and mirror using the tarball scripts already in the tree. (5) Ship a built artefact. ROOT gets away with source builds because it also ships binaries, conda packages and containers; CBS has no such budget, which makes a container image or a conda/spack recipe the cheapest route to “it runs” — and the one that does not need every user to become a C++ build engineer.

15 · what the paper owes a reader

Ten questions the source cannot answer

Everything so far describes what CBS does. Writing it up surfaced a different list: things a referee will ask that no file in the tree settles. Three of them change the published numbers. Sorted by what they cost if they stay unanswered.

3 · changes the numbers

Settings and modelling

  • check_histogram defaults to false. On, it adds 23 signal regions across 2 analyses. State which setting produced the results — better, echo it into the output JSON.
  • VR jets are never smeared. They are excluded from JER by being variable-R, at BuckFast.cpp:48,56. Either it is deliberate and one sentence closes it, or it is an unquantified systematic on both VR analyses.
  • Which of the twelve are validated? 5 carry no cutflow instrumentation; 3 say in their own comments that they are unfinished.
4 · blocks a rerun

Reproducibility and compatibility

  • The defaults ship with nobody. CBS_yaml/ is gitignored, so the file every run depends on is not in the repository, and a missing one is silent.
  • 3 keys are overruled, 3 are read by nothing. Of 14 keys in the original example, only 3 are still genuinely the user's.
  • The version table has a contradiction. At HEAD, cmake names Contur 2.1.1 and points at a patch that does not exist; the frontend says 3.0.0. HEAD is the only ref of four that disagrees with itself.
  • 123 registered names were retired. Deprecation aliases or a clean break — but not silence, and not a mapping that lives only in .cpp comments.
3 · needs a decision

Interface, install, and scope

  • Is the JSON a contract? It carries schema_version, which is a promise, but the term_id grammar every consumer parses is written down nowhere.
  • What install route does the paper give? Slide 14, restated: a paper with no followable build is a paper nobody reproduces.
  • What does “CBS” even name? — below.
Answer the scope question first. This deck is baselined at the merge-base, because it answers “what did I change”. A paper is baselined against released GAMBIT, because it answers “what is CBS”. Those are different sets, and the gap is real: ONNX (5 files) and MET significance (7) are absent from master entirely, predate the branch point, and so appear nowhere in this deck — correctly by its rule, and wrongly by the paper's. Pick the baseline and several other answers follow.

16 · next

Where this goes

For the collaboration to decide

Does upstream want the report-number naming migration, and does it need an alias table so existing YAML keeps working?

Should the CBS runner (solo_*) be proposed to master, or stay a branch tool?

Known work remaining

EXOT-2018-60 published selection · B2G-18-003 3T/2M1L digitisation · regression tests over the JSON schema · explicit implementation-status field in .info metadata so "registered" and "validated" cannot be confused again.

What this branch did not change

CBS changes how ColliderBit is invoked — a standalone runner, its own input and output path — not the physics underneath it. The existing analysis code was not rewritten to accommodate it.

The jet pipeline is the measurable case: the fixed-R branch of the event conversion is 336 tokens before and 336 after, 99.4% identical, and the only difference is a two-argument reorder from an unrelated commit. Variable-R jets were threaded through that same path rather than built beside it.

So the question for a reviewer is not whether old results moved. It is whether the new capability — 12 analyses, VR jets, histogram signal regions — is correct on its own terms, and slide 13 says plainly where that is not yet established.
