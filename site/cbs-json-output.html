01 · document shape

Eight top-level keys, two of them conditional

One document per run. Six keys are always written; sampling_advice and contur appear only when their feature ran. Click a numbered node to jump to its card.

The order above is emission order, not file order. nlohmann::json defaults to std::map for objects (Utils/include/gambit/Utils/json.hpp:3521), so keys land in the file alphabetically: analyses, contur, predefined_sets, run, sampling_advice, schema_version, summary, terms. A consumer must never depend on key order — and a reviewer comparing two output files should not read a reordering as a change.

03 · the payload

Nesting under one analysis

Two levels of the document are keyed by run data rather than by the schema: the analysis name, and the signal-region label. Everything below them has fixed field names.

Dynamic keys are convenient to read and awkward to validate — a schema checker cannot enumerate them, and a diff tool will report an added analysis as a wholesale subtree change. The flat terms array in section 04 exists partly to give consumers a fixed-shape alternative.

The flags carry the arithmetic rules the numbers cannot. Signal-region terms are safe_to_sum: false because the SRs of one analysis overlap — summing them double-counts events. Only the per-analysis combined terms and the Contur total are true. Alternative variants of the same quantity share an exclusive_group: pick one per group, never add them. A consumer that ignores these flags and sums the loglike column will get a confident, wrong number, which is exactly why they are in the file rather than in a README.

predefined_sets.default_total is the ready-made answer: the list of term_ids the emitter guarantees is a valid sum. Start there, and treat everything else as opt-in.

41 of the 106 emitted fields are read back by these 7 functions, matched on receiver and key so that a name shared by two objects — name on both a cutflow and a histogram, analyses at both the root and inside sampling_advice — is not credited to the wrong one. Renaming a read-back field breaks batch mode itself, not just a downstream plot script.

What the merge pointedly does not read is as informative as what it does. Every log-likelihood is emit-only: loglike, alt_loglikes and the whole combination block are ignored on the way back in. The merge combines yields and then recomputes the likelihood from the merged numbers, because averaging per-file log-likelihoods is not the same quantity and would be quietly wrong. The other unread fields — nbins, integral, bin_index, x_low, x_high, error, sr_label — are conveniences for a human or a plotting script, each recomputable from edges, counts and sumw2.

The combination arithmetic these guards protect: files of the same process are combined with event-count weights that sum to one, so the process keeps its full cross section; yields across different processes then add linearly, while their MC errors accumulate in quadrature.

One asymmetry worth knowing before reading a batch cutflow. Histograms are scaled by the process weight before being accumulated; cutflow counts are not — they are added raw. That is self-consistent for a cutflow read as "how many MC events survived each cut", but it means a batch cutflow table is not a luminosity-scaled yield and its rows do not correspond to the scaled numbers in signal_regions. Worth stating explicitly to anyone about to quote a cutflow from a multi-process run.
